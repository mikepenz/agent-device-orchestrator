How it works

One SQLite file is the coordinator. Every devq process reads and writes it.

The coordinator

  • The state lives in $DEVQ_HOME/devq.db (default ~/.devq), in WAL mode.
  • A tick under the database lock reaps timeouts, orphaned pids and abandoned waiters, then hands free devices to the oldest compatible request.
  • devq live is the same binary serving an embedded page. There is no separate daemon.

Waiting is polling. A ticket that is not polled for 8s is skipped when devices are handed out, and one not polled for 30s ends as abandoned.

Slots and limits

  • Expect and max. --expect is the realistic hold time, --max the hard limit. devq run sends SIGTERM to the command's process group at --max, then SIGKILL 5s later.
  • Orphans. devq run records its pid. If it is killed, the next devq process notices, kills the group and ends the slot as orphaned.
  • Advisory lock. Nothing stops a process from running adb against a device it does not hold. Use the hook as a guardrail.

Platforms

  • macOS is the primary, fully tested platform.
  • Linux is tested in a Linux container without a device, plus CI on Ubuntu. devq service is macOS-only; run devq live from a systemd user unit instead.
  • Windows is compile-checked only. Commands are force-killed with no grace period, and grandchildren of an exited leader are not killed.

Supply chain

Dependencies are exact pins, no crate younger than 7 days, cargo deny and cargo audit gate CI, and every GitHub Action is pinned to a commit SHA. Details are in the README.
